# Backend, Security, AI/Agent & Browser-Worker Audit

Covers: all 10 `apps/api/src/modules/*.controller.ts`, `apps/api/src/common/*`, `apps/api/src/app.module.ts`/`main.ts`, `packages/security`, `packages/agents`, `packages/workflow-engine`, `packages/contracts`, `packages/gcp`, `apps/browser-worker/src/{engine,browser,main}.ts`, `packages/database/prisma/schema.prisma`. All files were read in full. See `final-gap-report.md` §5, §9–13, §15–16 for the synthesized findings; this file is the full supporting evidence and reasoning.

## Authentication (`apps/api/src/common/auth.guard.ts`, `apps/api/src/modules/auth.controller.ts`)

Two parallel, incompatible identity systems exist:

1. **Firebase/Google** — `AuthGuard.canActivate` verifies `Authorization: Bearer <token>` via `getAuth().verifyIdToken()`, then `prisma.user.upsert({where:{identityProviderUid: token.uid}, ...})`. This is the only path the frontend's `api()` helper (`apps/web/src/lib/api.ts:14-18`) ever attaches a token for.
2. **Local email/password** — `POST /api/v1/auth/login-email` (`auth.controller.ts:50-96`) validates `email`+`password` against `passwordHash` (SHA-256 with a **hardcoded global salt** `":webpilot_salt_2026"`, `auth.controller.ts:29-31` — no per-user salt, no bcrypt/scrypt/argon2) and returns a plain JSON user object with **no token, cookie, or session of any kind**.

These two systems never bridge. Every `User` created through the local system (workspace "Add Member" with a password, or an approved onboarding request) gets a **synthetic** `identityProviderUid` (`user-${Date.now()}-${random}`, `workspaces.controller.ts:75`, `approvals.controller.ts:47`) — never a real Firebase UID. Consequences, both independently confirmed by reading the exact upsert/unique-constraint logic:

- **The password login path produces no artifact the API guard will ever accept**, so any user who authenticates this way gets 401'd on every subsequent call (`final-gap-report.md` F-1). `LOCAL_AUTH_BYPASS=true` masks this in every environment this repo ships (docker-compose, `.env.example`), which is exactly why it was never caught by the demo/test flow.
- **If a synthetic-UID user's email later matches a real Google account**, `AuthGuard`'s `upsert` on `identityProviderUid` finds no match and attempts a `create`, which collides with the pre-existing row on `User.email @unique` (`schema.prisma:46`) — an unhandled Prisma `P2002`, surfaced as a raw 500 with no `try/catch` anywhere in the guard (F-2).

`LOCAL_AUTH_BYPASS === "true"` (`auth.guard.ts:12,37-40`) skips Firebase initialization entirely and maps every request to a single fixed `local-demo-user` / `process.env.LOCAL_USER_EMAIL`. This is purely env-flag gated with no `NODE_ENV` cross-check — nothing in the guard itself would prevent this from silently authenticating every request as the same user if the flag were ever accidentally left `true` in a production environment file.

## Authorization pattern (`apps/api/src/common/context.ts`)

`requireWorkspace(userId, workspaceId?, roles?)` is the single authorization primitive used by all 10 controllers. When `workspaceId` is omitted, it falls back to the caller's *first* membership (`orderBy: {id:"asc"}`) rather than erroring — a correctness quirk (silently operates on "whichever workspace happens to be first" if the frontend forgets to pass one) but not itself an authorization bypass, since role/membership is still checked against whatever workspace resolves.

**The dominant pattern across controllers is correct**: fetch the resource by raw ID first, then call `requireWorkspace(user.id, resource.workspaceId, roles)` before returning or mutating anything — so even though resources are fetched by bare ID, unauthorized callers are rejected before any data leaves the request. This pattern was checked explicitly in `agents.controller.ts`, `runs.controller.ts`, `schedules.controller.ts`, `connections.controller.ts`, `approvals.controller.ts`, `workspaces.controller.ts` and holds consistently.

**Two confirmed exceptions:**
- `agents.controller.ts:364-371` — `DELETE /agents/:id` permits role `VIEWER` alongside `OWNER/ADMIN/OPERATOR`, the only mutating endpoint in the controller that does so (every other one explicitly excludes `VIEWER`). Cascades through `RunEvent`/`RunStep`/`Approval`/`ModelInvocation`/`Run`/`Schedule`/`AgentVersion`/`Agent` in one transaction. **(F-7, P0)**
- `runs.controller.ts:186-231` — `GET /:id/artifact` is `@Public()`, and even when a caller is authenticated, a `ForbiddenException` from `requireWorkspace` is caught and silently ignored ("Allow public image viewing"). `artifactPath` is a raw, unvalidated query parameter passed straight into `ArtifactStore.get()` with no check that it belongs to the run identified by `:id`. **(F-3, P0 — the one confirmed exploitable access-control bug in this audit.)**

## CRUD-adjacent correctness bugs found by direct code reading

- **`schedules.controller.ts:124-141`** (`update`) — writes `name`/`cronExpression`/`enabled`/`timezone` to the DB but never calls `SchedulerService().upsert(...)` again. **`trigger()` (:61-93) never checks `schedule.enabled` before creating a Run.** Together: editing a schedule's cron does nothing to the real Cloud Scheduler job (which keeps firing on the old schedule forever), and disabling a schedule has zero effect on whether it keeps executing. **(F-8, P0.)**
- **`admin.controller.ts:129-176`** (`purgeData`) — the Zod-adjacent type signature declares `target: "RUNS"|"AGENTS"|"SCHEDULES"|"FACTORY_RESET"`, but the `if/else if` chain only implements `"RUNS"` and `"FACTORY_RESET"`. Calling with `"AGENTS"` or `"SCHEDULES"` silently falls through to `count = 0`, writes an audit log claiming `PURGE_AGENTS`/`PURGE_SCHEDULES` happened, and returns `{ok:true, purgedCount:0}` — a fake-success no-op.
- **`runs.controller.ts:176-184`** (`cancel`) — flips `status: "CANCELLED"` in the DB only. Nothing in `engine.ts`'s `discover()`/`fast()` step loops polls run status mid-execution, so an in-flight browser automation cannot actually be interrupted — "Cancel" is a lazy/soft flag with no forceful preemption.
- **`agents.controller.ts:105-114,117-131`** — Two hardcoded, demo-specific business-logic special cases embedded directly in the create-agent endpoint: (1) if the AI-inferred `startUrl` doesn't contain the literal string `"google.com"`, it overwrites the stored `targetUrl` with the AI's inference; (2) if the agent name starts with the literal string `"Public Scraper"`, the name/description are rewritten from the plan summary. Both are clearly built around one specific demo flow (typing a generic URL like `google.com` and letting the AI infer the real target site) rather than general product logic.

## `packages/security/src/index.ts` — SSRF/domain-boundary guard

`assertSafeUrl(raw, allowedDomains?)` is real and does the right things by default: protocol allowlist (http/https only), a private-IP check covering RFC1918 ranges + loopback + link-local (including the GCP metadata IP range `169.254.169.254`) + IPv6 unique-local/link-local, and a DNS-resolution check (rejects targets that don't resolve, or that resolve to a private IP) run against the *resolved* address, not just the literal hostname — meaning simple SSRF-via-hostname tricks are caught.

**`ALLOW_PRIVATE_DEMO=true` is a global kill-switch, not scoped to the demo host despite its name.** Reading the exact condition at `:100-106`: `if ((!answers.length && !(ALLOW_PRIVATE_DEMO && hostname==="demo-portal")) || (answers.some(privateIp) && ALLOW_PRIVATE_DEMO !== "true")) throw`. When `ALLOW_PRIVATE_DEMO` is `"true"`, the second clause is always false regardless of hostname — meaning **every** private-IP target is allowed through, for **any** hostname, not just `demo-portal`/`localhost`/`127.0.0.1`. It is correctly set to `false` in the real production deploy path (`cloudbuild.yaml`, confirmed by the infra audit), but the flag's scope doesn't match its name, which is a landmine for a future copy-paste into a production env file. **(F-14, P2.)**

The `allowedDomains` matching logic (:75-93) treats a bare `"*"` or `"all"` entry as a full wildcard (intentional, user-facing feature), and — as a side effect of the wildcard-stripping regex (`d.replace(/^\*\./,"")`) — an allowlist entry that reduces to an empty string after stripping (e.g., a bare `"*."`) also matches any host, since `!clean` short-circuits to `true`. Low-likelihood (`.filter(Boolean)` already strips actually-empty strings before this loop runs; only a literal `"*."` string reaches this branch), but worth a defensive fix.

`redactSecrets()` is a best-effort regex over common secret-looking key names (`authorization|password|token|cookie|secret`) — reasonable as a defense-in-depth layer on logged DOM/error text, not a complete secret scanner by design.

`WEB_CONTENT_BOUNDARY` is a static instruction string consistently included in the Planner/Navigator/Recovery agent prompts — a real, working, but purely prompt-level mitigation for prompt injection (see AI section below for the structural backstop it relies on).

## `packages/agents/src/index.ts` + `orchestrator.ts` — AI/ADK/Gemini reality check

**Real usage, not decorative.** Genuine `@google/adk` (`LlmAgent`, `InMemoryRunner`) and `@google/genai` (`GoogleGenAI`) SDK calls; genuine structured output via `zodToJsonSchema` → `responseSchema`; a genuine fallback (ADK empty response → direct `GoogleGenAI.generateContent` call) with real exponential-backoff + jitter retry (4 attempts) on that fallback path; genuine JSON-recovery attempts on malformed model output (`runJson`'s catch-and-retry-with-appended-braces logic).

**Not the deep multi-agent system the naming implies.** Each of the four functions (`planWorkflow`/`navigateDiscovery`/`recoverWorkflow`/`verifyRecovery`) is an independent, single-shot call: `disallowTransferToParent`/`disallowTransferToPeers` are both set on every `LlmAgent`, and `InMemoryRunner.sessionService.createSession()` is called fresh on every single invocation and discarded immediately after — there is no persistent session/state across calls, no agent-to-agent handoff, and no in-call tool-use loop. This is honestly closer to **"four independently-invoked structured prompt→validated-JSON calls with retry/fallback"** than a true agentic system with memory or live orchestration. Not a criticism of the engineering — it's a reasonable, working design — but a correction to how the README frames it ("Google ADK TypeScript Planner, live Navigator... sessions/state used?" — technically touched, not meaningfully leveraged).

**`MOCK_AI=true`** (`:352-398,417-440,471-481,503-509`) makes all four functions return fully hardcoded, canned responses. `planWorkflow`'s mock branch is the most consequential: it returns a fixed "Monitor supplier purchase-order exceptions" plan with hardcoded CSS selectors regardless of the actual `goal`/`targetUrl` passed in. Confirmed (via the infra audit) that this is the default for the documented `docker compose up` demo path. **(F-4, P0.)**

**`orchestrator.ts`'s `MultiAgentOrchestrator`** (registry pattern, `IAgent` interface, saga lifecycle with `phase_changed`/`agent_invoked`/`step_executed` events, `handleFailureSaga`) is a fully-built, well-structured alternative orchestration abstraction — and it is **never instantiated anywhere in the codebase**. Repo-wide grep for `MultiAgentOrchestrator`/`registerAgent`/`.orchestrate(` finds zero call sites outside the file's own declaration (and its compiled `.d.ts`). The real execution path (`apps/browser-worker/src/engine.ts`) uses its own bespoke `discover()`/`fast()`/`recover()` functions instead. This class was introduced in the commit titled *"feat: implement enterprise multi-agent orchestrator"* — the commit message oversells what was actually added: an unused class. **Dead code.**

## `packages/workflow-engine/src/index.ts`

`applyPatch`/`nextVersionLabel`/`compileAuditArtifact` are all straightforward, correct, and match their README description exactly — `compileAuditArtifact` genuinely only produces a plain-text export artifact (confirmed via repo-wide `eval`/`new Function`/`exec`/`spawn` grep returning zero hits outside this one non-executed template-string generator) and is never evaluated dynamically anywhere in the codebase.

**`classifyRisk`** (:22-39) is the one real gap: `CLICK` actions get whatever `step.risk` the model assigned, defaulting to `LOW` per the Zod schema default (`packages/contracts/src/index.ts:48`), with **no independent, non-LLM classifier** forcing elevation for description/URL patterns that look dangerous ("delete", "pay", "purchase", "submit"). Since `requiresApproval()` in `engine.ts` only pauses for `HIGH`, the entire human-approval safety net for click actions is delegated to the same model whose output it exists to check. **(F-6, P1.)**

## `apps/browser-worker/src/engine.ts` + `browser.ts` — execution engine

**This is the best-implemented subsystem in the repository**, verified end-to-end:

- **Lease-based concurrency control** (`executeRun:210-221`) — `updateMany` with a `WHERE status NOT IN (...) AND (leaseExpiresAt IS NULL OR expired)` guard, atomically claiming a run; a second worker racing for the same run gets `count: 0` and exits early as a no-op duplicate. Real, correct optimistic locking.
- **Fast path is genuinely zero-LLM** (`fast()`, :550-620) — the step loop calls `executeStep` directly against the frozen `WorkflowSpec`, with no model call anywhere in the happy path; a model is invoked only inside `recover()`, on failure.
- **Self-healing loop** (`recover()`, :621-801) is fully implemented per the audit's own definition of "done": failure → DOM+screenshot captured → `recoverWorkflow()` (Gemini) → `applyPatch()` → `sandboxVerify()` (replays the patch in a **fresh headless browser context**, explicitly refusing to replay past any step that classifies as `HIGH` risk, :809-814,823-828) → `verifyRecovery()` (an independent Gemini call, explicitly instructed "the repair agent cannot approve itself") → a `RecoveryAttempt` row is persisted → on `PASS`, a new immutable `DRAFT` version is created → risk-gated: `LOW` + `autoPromoteLowRisk` auto-promotes to `PRODUCTION` in the same transaction that resumes the run; anything else creates an `Approval` row and pauses (`WAITING_RECOVERY_APPROVAL`). `executeRun()`'s entry path (:234-261) correctly checks for an already-approved `RECOVERY` approval and promotes+resumes before falling into discovery/fast dispatch. Every stage the audit brief's self-healing checklist asks for is genuinely present and wired.
- **Anti-loop guard** during discovery (:362-373) — terminates after 2 consecutive identical actions, preventing infinite navigation loops.
- **Network-level SSRF guard** (`installNetworkGuard`, `browser.ts:26-35`) routes *every* sub-resource request (not just top-level navigation) through `assertSafeUrl` — real defense-in-depth, though it performs a live DNS lookup per request, a real (not just theoretical) latency/flakiness risk on resource-heavy pages.
- **Clean lifecycle** — every entry point (`discover`/`fast`/`sandboxVerify`) wraps browser usage in `try/finally { await browser.close() }`.

**Real gap: stale-data replay risk.** `executeStep`'s `EXTRACT` (`browser.ts:255-265`) and `DONE` (:267-276) cases both prioritize a literal, pre-serialized JSON array embedded in `step.value` over live extraction — `if (step.value?.trim().startsWith("[")) return JSON.parse(step.value)`. Since `step.value` for a persisted `WorkflowStep` is frozen at discovery time (whatever the Navigator/Gemini response happened to put there), **any workflow whose discovery-time Navigator response embedded extracted records directly into `value` will replay that exact frozen dataset on every future fast-path run, forever, without ever touching the live page.** This directly undercuts the "healthy repeat run re-scrapes the live site" premise the self-healing narrative depends on. **(F-5, P1 — see `final-gap-report.md` for the fix and test recommendation.)**

**Generic extraction fallback is heuristic, not schema-driven.** When no frozen value exists, `extractRecords()` (`browser.ts:67-161`) falls back to a hardcoded CSS-selector guessing strategy (`[class*='product']`, `div[class*='cPH']`, `div[class*='75W']` — the latter two are **Flipkart-specific hashed CSS module class names**) plus keyword-based field-name matching (`fieldKey.includes("price")` → regex-scan for a currency-looking line), rather than using the specific `locator`s the extraction schema actually defines per field. This means the "AI-designed extraction schema" is largely decorative at fast-path replay time for any step relying on this fallback — the real field-to-value mapping comes from generic heuristics tuned around one specific demo site, not from the schema Gemini designed.

**`detectChallenge`** (`browser.ts:56-66`) is a naive `innerText().toLowerCase()` regex match for `captcha|verify you are human|cloudflare|turnstile|hcaptcha|recaptcha`. Real modern challenge widgets (Cloudflare Turnstile, reCAPTCHA v3) are frequently rendered inside iframes or as near-textless UI, which this check would likely miss, producing a false negative (execution proceeds and fails with a generic error instead of gracefully pausing for human verification). Classified 🟡 Partial, not broken — it does work for the demo portal's own text-based fake CAPTCHA.

**`apps/browser-worker/src/main.ts:9-13`** — the internal `/internal/runs/:runId/execute` endpoint only checks the `x-internal-token` header **when `LOCAL_TASKS === "true"`**; in real Cloud Tasks/production mode, this app-level check is skipped entirely, relying solely on Cloud Run's IAM-based OIDC invoker authentication being correctly configured (private ingress + `roles/run.invoker` restricted to the `task_invoker` SA). The infra audit confirms this is in fact how `cloudbuild.yaml` deploys it (`--no-allow-unauthenticated`) — so this is the correct GCP-native pattern in practice, contingent on that deploy configuration never regressing. Worth a comment in the code noting the security model shifts entirely to infra-layer enforcement outside `LOCAL_TASKS` mode. The token comparison itself (`!==`) is also not timing-safe, unlike the Slack signature check elsewhere in the codebase — low real-world exploitability, noted for consistency (F-15, P3).

## `packages/database/prisma/schema.prisma`

16 models. Cascade behavior is correctly configured at the DB level: every child table (`AgentVersion`, `Run`, `RunStep`, `RunEvent`, `ModelInvocation`, `RecoveryAttempt`, `Approval`, `Schedule`, `Integration`, `Connection`, `WorkspaceMember`) declares `onDelete: Cascade` back to its parent (`Agent`/`Run`/`Workspace`), so workspace/agent/run deletion is DB-safe by construction — the manual-cascade delete arrays present in several controllers are partially redundant with this but not incorrect.

**One real schema defect**: `WorkspaceSetting` (:309-322) has **no `@relation` field to `Workspace` at all** — `workspaceId` is a bare `@id` string with no foreign key. Deleting a workspace leaves its `WorkspaceSetting` row permanently orphaned (no cascade possible without a relation to cascade through), and nothing at the schema level enforces that a `WorkspaceSetting.workspaceId` references a real workspace. Low severity, real, worth a follow-up migration adding the missing FK + cascade.
