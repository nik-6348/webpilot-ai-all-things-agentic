01 · Product Overview

Understand the web once. Run it forever.

Most browser-automation tools either replay a brittle fixed script, or call a language model on every single step — slow, expensive, and non-deterministic. WebPilot AI does neither by default: it learns a task once with a live agent, then runs it deterministically, and only calls the model again when the page actually changes.

4

0

5
Independently deployed services
100%
Typed workflow, no generated code execution

The problem

Web automation either breaks the moment a site's DOM changes, or re-runs an LLM on every click — burning tokens and latency on pages that haven't changed at all.

The approach

A goal in plain English becomes an approval-ready, typed WorkflowSpec. Healthy runs replay it with Playwright, zero reasoning calls. A break triggers a bounded, verified repair — not a re-plan.

The outcome

Cheaper, faster, auditable repeat runs; and when the web does change, a self-heal loop with an independent verifier before anything is trusted or auto-promoted.

A real run, including a real recovery

1
First run (Discovery). Goal: "open Flipkart, extract the top 5 phones by price." The Navigator agent drives a real browser step by step and the run hits a "Are you a human?" interstitial.
2
Self-heal. The Recovery agent diagnoses the block and patches the single failing step; an independent Verifier checks the patch in a sandbox replay before it's trusted (confidence 0.95).
3
Promoted & resumed. The patch is promoted to workflow v1.2 and the same run resumes and completes — no human paged for a low-risk, high-confidence fix.
4
Every run after. v1.2 replays deterministically with Playwright — modelCallCount = 0 — until the site changes again.

02 · System Design

Design principles that hold the platform together

Four decisions shape everything else: workflows are typed and immutable, execution is deterministic by default, recovery is bounded and independently checked, and the browser's content is never trusted as instruction.

Typed, immutable WorkflowSpec

A learned workflow is a Zod-validated, versioned document — never model-generated code. Nothing is ever passed to eval() or new Function(). Each repair creates a new immutable version (v1.0 → v1.1 → v1.2…), so any run can be traced back to the exact spec that produced it.

Fast Path vs. Discovery

Discovery runs live, model-driven navigation to learn a workflow. Fast Path replays the stored spec with Playwright directly — zero Gemini calls — until a step's locator stops matching, which is the only trigger for falling back to reasoning.

Bounded, verified self-healing

Recovery only ever patches the one broken step — it cannot redesign the workflow. The patch is sandbox-replayed, then judged by a separate Verifier agent that never sees Recovery's reasoning, so the agent that wrote a fix can't be the one that approves it.

Risk-gated autonomy

A patch only auto-promotes on low risk + high verifier confidence. Anything else — high-risk actions (checkout, delete, pay), CAPTCHA/human-verification, low-confidence patches — pauses the run and creates a real Approval row for a human.

Web content is untrusted evidence

DOM text and screenshots are evidence for the Navigator to reason about, never instructions to follow — a prompt-injection boundary enforced in the agent contract, alongside SSRF/private-network/metadata blocking and an allowed-domain boundary the Planner can never widen.

Multi-tenant by construction

Workspace-scoped RBAC, an audit log, idempotency keys on every run, and worker leases with step checkpoints so a duplicate Cloud Tasks delivery or a second worker instance can never double-execute the same run.

05 · AI Agents & Async Dispatch

Four narrow agents, one dispatch path

Not one do-everything agent — four single-purpose Gemini calls, each with its own contract. Real @google/adk (LlmAgent + InMemoryRunner) and @google/genai (Vertex AI) calls, Zod-validated structured output, retries with backoff.

AgentCalled fromInputOutputConstraint
PlannerAPI, on agent creationgoal + target URL + allowed domainsa typed plan + extraction schemacan never widen the allowed-domain boundary
NavigatorWorker, during Discoverycurrent DOM (compacted) + screenshot + step historyexactly one next browser action, or "done"webpage content is untrusted evidence, never an instruction
RecoveryWorker, on a Fast Path failurethe failed step + error + current DOM/screenshota minimal single-step patchonly touches the one broken step, never redesigns the workflow
VerifierWorker, after a sandbox replay of a patchthe patch + the sandbox replay resultPASS/FAIL + confidenceindependent of Recovery — cannot approve its own patch

Every run takes the same dispatch path

Manual, scheduled, or Slack-triggered — nothing calls the browser worker directly.

06 · Google Cloud Services

What's actually running in production

Every service below is live in the deployed environment — provisioned via scripts/gcp-provision.sh, deployed via scripts/deploy.sh, and mirrored as Terraform in infra/terraform/main.tf.

ServiceRole in WebPilot AI
Cloud RunHosts all 5 deployables: web (public), api (public), browser-worker (private, Cloud Tasks-only ingress), notifier (private, Pub/Sub-only), demo-portal (public, deterministic DOM-drift demo).
Cloud SQL (PostgreSQL 17)Relational domain model via Prisma 7 — agents, immutable workflow versions, runs, run events, approvals, schedules, workspace/RBAC, audit log.
Vertex AI / Gemini 3.7 FlashModel backend for all four agents (Planner, Navigator, Recovery, Verifier) via Google ADK's LlmAgent + @google/genai.
Cloud TasksDurable, OIDC-authenticated dispatch of every run (manual, scheduled, or Slack-triggered) from the API to the private worker.
Cloud SchedulerReal cron jobs backing every user-created schedule, OIDC-signed, synced on create/update/delete — not a polling loop.
Pub/SubOperational event bus from the worker to the notifier (run completed/failed/needs-approval).
Cloud StorageRun artifacts — screenshots, DOM snapshots, extraction results — served back to the UI via short-lived HMAC-signed URLs.
Secret ManagerDatabase URL, per-workspace Slack/Gmail/Chat OAuth credentials, created and read at runtime — no secrets in images or env files.
Identity Platform / Firebase AuthGoogle sign-in, plus a custom-token bridge (createCustomToken) for the email/password login path.
Artifact RegistryDocker image storage for all 5 services, built by Cloud Build.
Cloud BuildBuilds and pushes each service image; incremental configs so a change to one service doesn't rebuild all five.
IAMSeven least-privilege service accounts (web, api, worker, notifier, plus three invoker-only identities for Tasks/Scheduler/Pub-Sub) — no service holds roles/editor or roles/owner.

07 · Implementation Status

What's actually implemented

Every item below exists in the running code and the live deployment — nothing here is aspirational.

Core execution

Typed WorkflowSpec, deterministic Playwright execution, no eval()/new Function() model-code execution. Zero-reasoning fast path on healthy repeat runs. Immutable agent versions with manual draft editing and activation.

Self-healing

Failure checkpoint → screenshot/DOM context → minimal repair → sandbox replay → independent verifier → low-risk auto-promotion or human approval → resume same run.

Human-in-the-loop

Plan approval, high-risk action approval, recovery approval, CAPTCHA/human-verification pause — real approval rows, not fire-and-forget automation.

Security

SSRF/private-network/metadata blocking in production, redirect/browser-request guard, allowed-domain boundary, web-content prompt-injection boundary, secret redaction.

Integrations

Slack OAuth with signed/expiring state and signed slash commands scoped to the connected workspace, Slack notifications, Gmail and Google Chat adapters.

Multi-tenancy

Workspace RBAC, audit log, idempotency keys, worker leases and step checkpoints, per-workspace login-method controls.
